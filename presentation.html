PortPulse · Data engineering project

From ETA events to trusted port-call data

A small, explainable pipeline that validates what arrives, keeps the evidence, and makes the current ETA easier to trust.

Phase 1: deterministic synthetic events · Phase 2: real Portnet V1 ETL

01 · The problem

An ETA is a changing observation

Data can be invalid

Missing or malformed fields should be explained, not silently accepted.

Data can repeat

Re-polls can deliver the same observation more than once.

Data can conflict

A later update can revise an earlier ETA, and timestamps have different meanings.

The goal is a traceable data process: retain what arrived, record quality outcomes, and make decisions explicit.

03 · Phase 1

A controlled first pipeline

JSONL fixture→Pydantic validation→PostgreSQL→Reconciliation→Query result
  • The fixture is synthetic and checked into the repository.
  • Bad rows are rejected with reasons; accepted events remain available for analysis.
  • Versioned rules choose a trusted state, and replay produces the same golden result.

04 · Trust and traceability

Keep the evidence behind the answer

Validate

Reject malformed events and keep a reason for each rejection.

Deduplicate carefully

Separate exact repeats from ID collisions; collided IDs cannot update trusted state.

Track three clocks

Source update, collection/receipt, and database ingestion each answer a different question.

A replayable fixture makes the core behavior explainable without depending on a live API.

05 · Phase 2

One supported live source

Digitraffic Portnet V1→Python adapter→Pydantic validation→PostgreSQL→Quality report
  • Accepted observations, rejected records, and quality issues go to dedicated Portnet tables.
  • ETA revisions are new observations; exact repeats and ID collisions are counted separately.
  • The supported path calls Portnet V1 only.

06 · Identity and time

A revision is not automatically a duplicate

For Portnet, an observation is identified by its port call, port area, and provider update timestamp.

Provider update time

When the source says its record changed.

Collection time

When PortPulse received the API response.

Ingestion time

When PostgreSQL stored the row.

Keeping these clocks separate helps explain delays and makes stored results auditable.

07 · What the evidence says

Separate live observations from test cases

One documented live run

125 records received: 59 active calls, 65 completed, and 1 without ETA. The 59 active calls yielded 59 accepted observations.

Injected reliability cases

Six deterministic tests cover invalid data, ambiguous areas, repeat polls, and ID collisions. These are synthetic test inputs.

Limits to state clearly

Live reports are snapshots. They do not prove long-term provider reliability or behavior across a continuing series of polls.

08 · A local walkthrough

Run the deterministic path yourself

Start PostgreSQL with Docker Compose, install the project requirements, then run:

python -m scripts.ingest_fixture
python -m scripts.reconcile
python -m scripts.query_state PC-DEMO-001

The expected trusted ETA is 2026-01-15 15:40 UTC, selected from the synthetic event history. For Portnet, use python -m scripts.ingest_portnet --date YYYY-MM-DD with a date supported by the API.

09 · What this project demonstrates

Trust comes from a visible process

  • Validate data at the boundary and keep rejected records explainable.
  • Make identity, deduplication, and time rules explicit.
  • Keep deterministic tests separate from live API evidence.
  • Store enough history to explain how a result was produced.

The result is a small pipeline that can be inspected, replayed, and extended in clear steps.
