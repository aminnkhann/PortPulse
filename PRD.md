## 1. Problem, user and value

**Problem.** Several systems can publish new ETA information for the same simulated vessel port call. Messages may arrive out of order, be repeated, contain invalid data, or disagree. Without explicit rules, the newest received message is not necessarily the most trustworthy value.

**Primary persona — port operations analyst.** Before a berth-planning meeting, the analyst needs to check the trusted ETA for a port call and understand which source/event established it and why another source disagrees. This is the MVP's primary job-to-be-done.

**Secondary persona — data engineer.** Needs reproducible validation, quarantine, and replay so data defects cannot silently change the result. Platform-support dashboards are **not** a separate P0 user journey.

**Value claim.** PortPulse is a **synthetic, educational demonstrator** of trustworthy operational state reconstruction. It does not diagnose defects at any specific company or prove operational savings in a real port.

## 2. Product goal, MVP output and measurable acceptance

**Goal:** Given a controlled JSON fixture for **one port call** and **three simulated source systems**, compute one deterministic trusted ETA (or an explicit unavailable status), explain the selection, and expose audit/quality issues.

**P0 input:** A versioned JSONL fixture generated by a deterministic Python script; a source-authority table; a rule configuration; and a fixed simulated evaluation time (**as_of_utc**).

**P0 output:** A queryable current port-call state, preserved event history, rejected/duplicate/conflict records, and a compact run summary. One SQL view or CLI response is sufficient; a web UI is not mandatory.

**Required G1 test artifact (to be created, not claimed as already implemented):**

- **scripts/generate_fixture.py → fixtures/port_call_v1.jsonl:** deterministic generator and approximately 30 synthetic message occurrences, including at least two exact duplicate occurrences; one repeated event ID with different content; two out-of-order arrivals; one conflict above the ETA tolerance; one invalid schema version; one delayed-but-newer event; and one stale-source example. A single event can exercise more than one rule.
- **fixtures/expected_output.json:** hand-reviewed golden current state, selected source/event IDs, active issues, and run counts.
- **rules/eta_rules_v1.yaml:** source precedence, eligibility, thresholds and tie-break rules.
- **docs/data_dictionary.md:** input fields, time semantics, units and synthetic source assumptions.

**Measurable acceptance:** Running the test fixture twice, and processing the same multiset of events in a different processing order, must produce the **same canonical trusted state and canonical issue set** as the golden file. The historical audit of processing attempts may have different wall-clock metadata; that metadata is not part of the business-state comparison. The test must demonstrate every declared error category and its reason.

## 4. Reconciliation and time rules — proposed v1 decisions for G1 sign-off

These are **simulation rules**, not DCSA-prescribed authority rankings or real port operating policies. The team may refine the values at G1; changes require a rule-version bump and golden-fixture review.

| Rule | P0 decision | Why it matters |
|---|---|---|
| R1 — identities | Key events by event_id; canonical hash covers source-owned payload fields, excluding pipeline-generated ingested_at. | Detect exact repeats vs ID reuse. |
| R2 — collision | If an event_id has two different payload hashes, exclude **all** versions of that ID from trusted state; log ID_COLLISION. | Reprocessing order cannot choose a different winner. |
| R3 — clocks | event_time = when source states the ETA update; eta_utc = predicted arrival; received_at = simulated arrival to platform (fixture); ingested_at = actual system load time, never used for business rules. | Replays stay deterministic. |
| R4 — source precedence | Example for ETA only: coordinator_sim (priority 3) > carrier_sim (2) > terminal_sim (1). | Defines authority explicitly. |
| R5 — within-source selection | For each source, choose latest eligible event_time; ties resolved by received_at then lexicographic event_id. | Later ingestion cannot replace a more recent message merely by arriving later. |
| R6 — freshness | Evaluate each source's latest eligible received_at against fixed as_of_utc; stale if older than **120 simulated minutes**. Unseen sources are unavailable. | Distinguishes source availability from ETA time. |
| R7 — trusted selection | Highest-priority **non-stale** source wins. If none qualifies, trusted ETA is null and status is UNAVAILABLE_STALE; retain last-known information separately for explanation only. | Never silently substitute stale data as current. |
| R8 — conflict | Compare the current eligible ETA of each non-stale source. A pairwise difference **greater than 30 minutes** creates a CONFLICT issue, even when precedence identifies a trusted winner. | Authority does not hide disagreement. |
| R9 — delivery delay | Flag DELAYED_DELIVERY if received_at − event_time **greater than 30 minutes**; delay is advisory, not automatic rejection. | Distinguishes latency from obsolete information. |
| R10 — deterministic time | Evaluate all records against fixed as_of_utc. Disallow records with received_at after this cutoff from influencing state. | Identical results across runs. |

**State computation order:** validate records → canonicalize payloads → detect exact duplicates/ID collisions → exclude invalid/collided IDs → choose per-source latest eligible ETA → mark stale sources → choose trusted source → calculate conflicts/delivery warnings → persist derived state and issues. For replay safety, the state can be recomputed from the eligible set rather than relying on first-arrival wins.

**Worked example (illustrative, before full fixture is authored):**

| Received | Input | Rule / outcome | Trusted ETA after processing |
|---|---|---|---|
| 09:05 | Carrier E01: event_time 09:00, ETA 15:00 | First eligible carrier update | 15:00 |
| 09:31 | Carrier E02: event_time 09:30, ETA 15:30 | Newer update from same source | 15:30 |
| 09:32 | E02 repeated unchanged | Exact duplicate counted | 15:30 |
| 09:40 | Carrier E00: event_time 08:50, ETA 14:50 | Out of order; audit only | 15:30 |
| 10:05 | Coordinator E04: event_time 10:00, ETA 15:45 | Higher-precedence fresh source | 15:45 |
| 10:12 | Terminal E05: event_time 10:10, ETA 16:30 | Conflict (>30 min); coordinator still wins | 15:45 + CONFLICT |

For this example, **as_of_utc = 11:00** on the chosen fixture day, so the three sources shown are within the 120-minute freshness window. The full fixture must also exercise staleness, delayed delivery, invalid payload and ID collision.

## 6. Implementation boundary / system outline

**Minimum P0 stack:** Python 3.12, Pydantic for event validation and JSON Schema generation, PostgreSQL, pytest, one CLI/SQL view and a simple Docker Compose setup for PostgreSQL. Rules belong in a small **pure reconciliation function** that can be unit-tested without a running database.

**Core tables:** `source_system`, `port_call`, `raw_event`, `rejected_event`, `quality_issue`, and `port_call_state`. The initial schema and source seed are in `migrations/001_create_core_tables.sql`; local PostgreSQL runs through `docker-compose.yml`. `raw_event` stores unique event ID/hash variants, allowing collisions to be retained; exact duplicate attempts are recorded as quality issues, and invalid payloads go to `rejected_event`.

**Pipeline:** Fixture JSONL → Python parser/validator → PostgreSQL raw/rejected records → deterministic state builder → state + issues → CLI/SQL readout. Raw ingestion time can be recorded for diagnostics but must not influence a replay's business outcome.

**Stretch phases (not required to pass Phase 1):** Phase 2/P1 may add the proposed Digitraffic Marine API input adapter, a richer read-only API, broader synthetic scenarios, database integration checks, and reporting/dashboard work. Phase 3/P2 may add Kafka, MinIO, Airflow, dbt, cloud services, streaming, lineage, terminal-equipment simulation, and DCSA conformance research. Keep both stretch phases optional and estimate them only after the MVP is complete.

### Phase 2 input: Digitraffic Marine API

This optional P1 input does not change the P0 synthetic fixture or v1 event contract. The adapter fetches active visits from the [Digitraffic Port Call V2 API](https://meri.digitraffic.fi/swagger/#/Port%20Call%20V2), validates and normalizes each response, then passes accepted ETA updates through the existing deduplication and reconciliation rules. Only the latest `Expected to Arrive` update can provide a trusted ETA; a later arrived, departed, or cancelled status makes that visit unavailable. The adapter retains the raw response; tests use fixed sample data and do not depend on a live API response.

The v2 adapter maps `visitId` to a namespaced PortPulse call identity, `eta` to `eta_utc`, and `updateTime` to the source update timestamp. It keeps status and port/vessel identifiers in the raw source payload. The event identity is derived from `visitId` and `updateTime`: the same identity and canonical payload is an exact duplicate; the same identity with different content is an ID collision; a changed `updateTime` is a new visit update. These distinctions remain visible in history and quality issues.

`digitraffic` is configured with a 120-minute freshness threshold and priority 1. Digitraffic call IDs use the `digitraffic:` prefix, so they remain separate from synthetic calls and Digitraffic wins its own fresh, valid visit. If records are later joined under one call ID, conflicts remain visible and the highest configured priority wins, followed by the existing event-time and tie-break rules. Current priorities are project assumptions, not claims about real-world authority. The first receipt time and database ingestion time are stored separately; replay uses saved events without refetching or changing business timestamps.

The adapter sends `Digitraffic-User` and `Accept-Encoding: gzip` headers and respects the API's request limits and update intervals. Any published data must include attribution under [Digitraffic's CC BY 4.0 terms](https://www.digitraffic.fi/en/terms-of-service/). This is Finnish marine traffic data, not broad port coverage or operational authority.

The marine comparison adapter may compare Portnet's agent/port/pilot ETA reports with vessel-reported AIS ETA when the vessel MMSI, destination port, and ETA date establish one unambiguous shared call. Calls with recorded actual arrival or departure times are ineligible. AIS ETA omits the year, so it uses the matching Portnet ETA's year. This is a source-comparison demonstration; the configured Portnet-over-AIS ranking is a project assumption, not an operational authority rule.

**External standards boundary:** [DCSA Port Call standards](https://dcsa.org/standards/port-call), with Port Call 2.0 as a **conceptual reference** for message vocabulary. The P0 JSON is deliberately simplified, synthetic and **not claimed DCSA-conformant**. Exact conformance/mapping is deferred.

**Non-goals:** No real terminal or vehicle control; no live TOS/ECS integration; no company-private APIs; no safety-critical operational decisions; no claim of production availability, throughput, or financial impact.

## 9. Acceptance/demo script

1. Run the frozen fixture at fixed as_of_utc and show the trusted ETA and selected source/event.
2. Replay an exact duplicate and show duplicate count without a second trusted record.
3. Insert a same-ID/different-payload record; show **ID_COLLISION** quarantine and deterministic exclusion.
4. Deliver an older event late; show history records it but a newer within-source ETA remains current.
5. Deliver a delayed-but-newer event; show its separate latency warning and legitimate eligibility.
6. Add a conflicting source; show both the trusted choice and **CONFLICT** explanation.
7. Show an invalid payload rejected with a reason, and a stale source flagged at the fixed evaluation time.
8. Query the SQL view/CLI, displaying trusted ETA, winner, applied rule and open issues.
9. Process the *same full event multiset* in a shuffled order and diff canonical output against **expected_output.json**. The golden comparison must pass.

**Definition of done:** PP-FR01 through PP-FR08 (including split 05/06), TC01–TC11, and PP-NFR01–07 have verifiable evidence; the rules, fixture and golden file are version-controlled; another group member can reproduce the demo; no unfinished P1 feature is described as complete.
